# Discovery: skill feedback sync (w-7ec48ee9, visit 1, attempt 1)

## Question
Where does the owner's input fit the existing code: a SessionStart GET to the history server for team-approved skill feedback newer than the local skill's last modification, which then auto-improves the local skill, and recording which skill versions each stage used?

## Answer
Recording the skill versions each stage uses **already exists**. `SkillLoaded` and `AgentStarted` events go on the observations stream, every version is kept under `.gofast/instructions/<sha256>/`, and `gf status`, the sync and the viewer all show them. The rest is **new**. The server has no "skill feedback" and no "approval" of it. Its only member judgement is the per-visit or per-work **assessment** (good, or went wrong with a reason). gf has never read anything from the server except stream heads and blob presence, and ADR 0001 forbids exactly this second direction of data flow. Skills are versioned by content hash, not by time. "The local skill's last modification" has no recorded meaning today, and the plugin directory is shared by every repository it is loaded into, while the server is per project.

## Questions for grill
1. **ADR 0001 conflict.** The input opens the second direction of data flow that ADR 0001 rejected, and has text from the server reach agents as instructions (E5, E6). Is this the "next step" the ADR anticipated, so the ADR is superseded by a new one? Which of its guarantees must still hold, for example "never approves, rejects or routes anything"?
2. **What "skill feedback" is.** The server has no such thing (E4). Is it the existing assessments, a new resource (feedback text tied to a skill and maybe a version), or a proposed new skill version (diff or full files)? Who writes it: a member in the viewer, an agent, or derived from went-wrong assessments?
3. **What "approved by the team" means.** No approval exists on the server (E4). Who approves (any member, the organisation, a quorum), where (the viewer), and can an approval be withdrawn? Is approval per project or per organisation, given one plugin serves every repository (E8)?
4. **"Later than the local skill's last modification".** Versions are content hashes with no time (E2), and file mtimes change on checkout (E9). Which clock decides: the git commit time of `plugin/skills/<name>/`, the file mtime, the time gf last applied feedback, or the base version the feedback was written against (a content hash, which the server already knows, E3)?
5. **What "auto-improve the local skill" does.** Does gf apply a server-provided new version verbatim, or does an agent rewrite the skill from feedback text? Does it run with or without the owner seeing or approving the change, and is it committed? The plugin dir is the owner's source of truth and may be another worktree or clone (E8, E12). Which directory is changed: `$CLAUDE_PLUGIN_ROOT`, or this repo's `plugin/`?
6. **Credentials for the GET.** gf only holds the project secret, which the server refuses for reads (E7, ADR 0002). Should the secret also be allowed to read approved feedback, or does gf need a member token?
7. **Session start behaviour.** SessionStart fires on startup, resume, clear and compact (E10). Should the check run on all of them, or startup only? What happens when the server is unreachable or sync isn't configured: silent, a message, or blocking? What happens if a stage visit is open when a skill changes underneath it?
8. **Tracking versions: what is missing?** Per-visit skill versions already exist (E1, E3). Does "keep track of skill versions being used in each stage" ask for something more, such as linking a version to the feedback that produced it, a human-readable version number (plugin.json stays 0.1.0, E11), or showing them in the viewer per stage?
9. **Scope of skills.** Does this cover only the owner's skills under `plugin/skills/` (aggregate-design, etc.), or also the agent definitions (`plugin/agents/*.md`) and vendored skills (grilling, domain-modeling, under MIT with SOURCE.md)?
